# Giftia

Giftiaを4人の班で改修するプロジェクトです。班で要求・要件を合意し、それに沿って開発します。

> このREADMEは班の運用ルールのたたき台です。班で確認・合意したうえで運用を開始してください。改修の要求・要件は後日話し合って決定します。既存の実装も、承認済みの改修仕様とはみなしません。

## 1. 班のメンバー

開発・レビューの担当はIssueごとに決めます。要求・要件や班のルールは4人で合意し、決定内容を記録します。

## 3. 文書の役割・配置

READMEにはプロジェクトの概要、共通ルール、関連文書への案内を記載します。要求・要件の詳細と、Issue・PRのひな形は別ファイルで管理します。

要求・要件の文書は、班で話し合うための見出しと未記入欄を用意しています。本文は未記入・未合意です。GitHub用ひな形の正式配置は今後整備します。

```text
.
├── README.md
├── AGENTS.md
├── docs/
│   ├── requirements/
│   │   ├── business_requirements.md   # 要求定義：実現したいこと
│   │   ├── system_requirements.md     # 要件定義：システムが満たす条件
│   │   └── traceability.md            # 要求・要件・Issue・PR・確認結果の対応
│   └── specifications/
│       └── 仕様.md                     # 必要になった実装詳細の補足
└── .github/                           # 今後正式配置するひな形
    ├── ISSUE_TEMPLATE/
    │   ├── task.md
    │   └── bug.md
    └── pull_request_template.md
```

| 文書 | 記入すること |
| --- | --- |
| [要求定義書](docs/requirements/business_requirements.md) | 背景、顧客理解、課題の選定、提供価値、要求、解決策の比較、検証方法、仮説の変遷 |
| [要件定義書](docs/requirements/system_requirements.md) | 対象範囲・Phase1、機能・画面・API、データ設計と供給、候補取得と順位、構成、非機能、制約、実装との整合 |
| [対応表](docs/requirements/traceability.md) | 要求 → 要件 → Issue → PR → 確認結果。要件定義書3章から参照し、対応表を二重管理しない |
| [仕様](docs/specifications/仕様.md) | 要件だけでは判断が分かれる実装詳細。必要な項目だけ記入し、要件の条件を変更しない |

### 班での記入・合意

- まず教材とテンプレートを確認し、要求定義書の顧客課題・提供価値・解決策を話し合います。その後、要件と最初に作る範囲、確認方法を具体化します。
- 要求・要件の正本は `docs/requirements/` の文書です。Issueは相談・作業、PRは変更・レビュー、仕様.mdは必要な実装詳細の記録に使います。
- 教材・テンプレートは参考資料です。顧客や施策、目標値の記入例を、班の合意として転記しません。事実・仮説・提案・合意済みの内容を区別し、根拠にはケース資料の該当箇所を添えます。
- 教材に合わせ、要求は `BR-001`、機能要件は `FR-001`、データ要件は `DR-001`、非機能要件は `NFR-001` の形式で採番します。IDは原則変更・再利用しません。
- 要件ごとに対応する要求IDと受け入れ条件・確認方法を記載し、対応表にリンクを追加します。1つの要求から複数の要件・Issueに分かれても構いません。
- 合意状況、合意日、確認した班員、合意したPRを記録します。未回答や未記入を合意とみなしません。作成日・合意日・期限をAIに推測で埋めさせません。
- テンプレートの週ごとの記入・仮確定・確定時期を参考に、班の進行を確認します。要求の確定後は原則固定し、変更が必要なら理由・影響をIssueで共有して4人で再合意します。
- 要求・要件の変更時は定義書と対応表、必要なら仕様も更新します。Slackの会話だけで仕様を確定しません。

## 4. 開発の進め方

1. 要求定義を作成し、利用者・課題・改修の目的・対象範囲を4人で合意する。
2. 要件定義を作成し、機能、対象外、制約、優先順位、受け入れ条件を4人で合意する。
3. 対応表を整備し、要件を実装可能な単位のIssueに分割する。
4. Issueの担当と完了条件を確認し、Slackで共有してから作業ブランチで開発する。
5. 動作確認の結果を添えてPRを提出し、レビューを受ける。
6. マージと完了条件の充足を確認し、Issue・対応表を更新してSlackで完了を共有する。

要求・要件が未合意の間は、調査、開発環境の整備、ルール作成を進めます。機能の追加・変更は、対応する要求・要件の合意後に着手します。

## 5. Issueの使い方

作業前にIssueを作成します。原則「1 Issue = 1つの目的」とし、大きな作業は分割します。

- タイトルは `[機能] ...`、`[不具合] ...`、`[整備] ...`、`[ドキュメント] ...` など、目的が分かる名前にする。
- 背景・目的、作業範囲・対象外、要求ID・要件IDと文書内の該当箇所へのリンク、完了条件、担当、確認担当、期限、未決事項を記載する。
- 実装Issueでは要求・要件の両方に紐づける。例：`BR-001 → FR-002 → Issue #12`。IDだけでなくリンクを添え、対応表にも同じ関係を記録する。
- 環境整備など要求・要件に直接対応しない作業は「対象外：開発環境整備」など理由を明記する。未決定の要求・要件に仮の紐づけをして、実装に着手しない。
- 不具合は、関連する要求・要件、再現手順、期待する結果、実際の結果、確認環境を記載する。対応する要件が不明な場合は調査から始める。
- 主担当は1人とし、GitHubのAssigneesに設定する。割り当て・変更はSlackでも共有する。
- 状態はIssue本文の先頭で「相談中 / 着手可能 / 作業中 / レビュー中 / 完了」を管理する。Projectsを導入する場合はそちらに統一してよい。
- 合意済みの要求・要件と完了条件が確認できたら「着手可能」にする。
- 完了条件には確認方法と証拠を示す。PRのマージだけで完了とせず、条件の充足を確認する。文書・調査のIssueは成果物と確認結果を記録して完了する。

## 6. ブランチ・コミットのルール

mainはレビュー済みの変更を集めるブランチとし、直接pushしません。最新のmainから作業ブランチを作ります。SourceTreeでも同じルールで操作します。

形式：`<種類>/<Issue番号>-<短い英語の説明>`

| 種類 | 用途 | 例 |
| --- | --- | --- |
| feature | 機能追加 | `feature/12-gift-search` |
| fix | 不具合修正 | `fix/23-search-error` |
| docs | ドキュメント | `docs/5-team-rules` |
| refactor | 振る舞いを変えない整理 | `refactor/31-api-client` |
| chore | 設定・環境整備 | `chore/8-eslint-config` |

- 半角英小文字、数字、ハイフンを使う。
- 原則、1つの作業ブランチは1つのIssueに対応させる。
- コミットは意味のまとまりごとに分け、`docs: 班の運用ルールを追加` のように変更内容を書く。
- 他の人の未完了の変更を無断で上書きしない。共有ブランチへのforce pushは行わず、競合は関係する担当者と確認して解消する。

## 7. PR・レビューのルール

1. 作業ブランチをpushし、main向けにPRを作成する。途中で相談する場合はDraft PRを使う。
2. タイトルは `docs: 班の運用ルールを追加` のように種類と変更内容を書く。
3. 本文に目的、関連Issue、要求ID・要件ID、変更内容、確認方法と結果、証拠、影響・未確認事項を記載する。画面変更には必要に応じてスクリーンショットを添える。
4. 自分以外の班員1人以上をReviewerに指定し、SlackでPRのリンクと確認してほしい内容を共有する。
5. 指摘を解消し、1人以上の承認を得たら作成者がマージする。要求・要件や班のルールを変更する場合は、4人全員の合意を記録してからマージする。未回答は同意とみなさない。
6. 原則Squash mergeを使い、不要になったブランチを削除する。班員は次の作業前にmainを更新する。

- Issueを完了するPRは `Closes #12`、部分対応は `Refs #12` と記載する。対応表にもPRへのリンクを追加する。
- レビューでは、合意済みの要求・要件・完了条件との一致、動作、読みやすさ、セキュリティを確認する。本人の承認だけではマージしない。
- フロントエンドのコード変更は原則 `npm run lint`、`npm run build`、関連する画面・操作を確認する。バックエンド・DBの確認手順は、それぞれの環境整備時に定める。
- 文書のみの変更は内容、リンク、IDの対応、表記を確認する。未確認や失敗がある場合は理由と影響を記載し、解消または班の合意までマージしない。
- AIが作成した変更も、担当者が内容を理解し、自分で確認して提出する。

GitHub側では、mainのブランチ保護、PR必須、承認1人以上、導入済みCIの成功必須を設定する方針です。実際の設定は別途行います。

## 8. Slackでの共有ルール

班で使用するSlackチャンネルに、対象のIssue・PRへのリンクを添えて共有します。

| タイミング | 共有する内容 |
| --- | --- |
| Issueの割り当て・変更時 | Issue、担当者、作業内容、期限 |
| 作業開始時 | Issue、着手する内容、ほかの人と重なりそうな作業 |
| 作業を実施したとき・作業終了時 | 実施内容、確認結果、残作業、次に行うこと |
| PR提出・レビュー依頼時 | PR、確認を依頼する相手、確認してほしい点 |
| マージ・Issue完了時 | Issue・PR、完了した内容、ほかの班員への影響 |
| 困りごと・遅れ・仕様の疑問があるとき | 状況、困っている点、相談したい相手・内容 |

Slackは気づいてもらうための共有に使い、決定事項・作業結果・レビュー内容はGitHubにも残します。Slackで決まった内容は担当者が文書・Issue・PRに反映し、反映先のリンクを共有します。

## 9. セキュリティの基本ルール

- `.env`、APIキー、DBの認証情報、パスワード、秘密鍵、個人情報をコミットしない。ログ、スクリーンショット、Issue、PR、Slackへの貼り付けにも注意する。
- ローカル用の秘密情報ファイルは `.gitignore` の対象にする。共有用の `.env.example` には変数名とダミー値だけを記載する。
- push前に差分と追加ファイルを確認する。ひな形のチェック欄だけで安全と判断しない。
- ブラウザに渡るコードや `NEXT_PUBLIC_` 付きの環境変数に秘密情報を置かない。DBへの接続・認証情報の利用はバックエンド側で行う。
- APIでは入力値の検証と必要な認証・権限確認を行う。DB操作では値をSQL文字列へ直接連結せず、パラメータ化されたクエリやORMを使用する。
- 共有DBの接続権限は必要な範囲に絞る。Workbenchでのデータ削除・スキーマ変更は、接続先と影響を確認し、関係する班員と相談してから行う。
- 開発・検証には原則ダミーデータを使う。実データを外部AIサービスへ入力しない。
- 秘密情報の漏えいに気づいたら、値を再掲せずリーダーへ速やかに連絡する。キー・認証情報を失効・再発行し、必要な履歴の対応を相談する。ファイルから削除しただけで対応完了としない。

具体的な認証方式・権限・データ保護などの要件は、要件定義で合意します。

## 10. フロントエンドの起動

Node.jsとnpmを用意し、このリポジトリのルートで実行します。

```bash
npm ci
npm run dev
```

ブラウザで http://localhost:3000 を開きます。バックエンドや環境変数の設定が必要な場合は担当者に確認してください。

```bash
npm run lint   # コードの静的チェック
npm run build  # 本番用ビルドの確認
npm start      # ビルド済みアプリの起動
```

AI向けの作業指示は [AGENTS.md](./AGENTS.md) に記載します。班のルールの変更時は、関連する文書の整合も確認します。
