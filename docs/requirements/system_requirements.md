## 1. システム化の範囲（with）

| 要求ID | 今回システムで実現するか | 理由 |
| --- | --- | --- |
| BR-01 | 実現する | タグ（5種類）で相手に合う商品に絞り、類似度の高い順に返す（FR-03・04、6.2）。Exhibit 5の「入力→候補取得→順位付け→結果」の中心になる |
| BR-02 | 実現する（BR-01に統合） | 一致したタグ名を商品カードに表示する。理由の文章は作らない。あわせて説明文の冒頭2行を表示する（FR-05、6.3） |
| BR-03 | 実現する（形を変える） | 予算+20%の追加提案は見送り、代わりに予算の下限・上限を500円単位で利用者が自分で選べるようにする（FR-08、11/14 チームMTG）。既存の検索APIは下限・上限に対応しているので、画面の変更だけで作れる |
| BR-04 | 測り方のみ | モックはローカルで動かすだけで、購入率は測れない（Exhibit 5）。本番に入れたあとに測る（要求定義書6章） |
| BR-05 | 測り方のみ | 単価の変化も本番に入れたあとに測る。予算の下限・上限の選択（FR-08）を入れた前後で比べる |
| BR-06 | 実現しない | 誕生日専用の入口は作らず、既存の検索画面を使う（11/12 チームMTG）。「誕生日ならGiftia」は長期の方向性として要求定義書に残す |
| BR-07 | 一部 | タグで見えるようになった商品で、出会えていない商品を減らす（FR-03・04）。予算の上限を自分で広げて、予算を少し超える商品も探せるようにする（FR-08） |

Exhibit 5の必須処理との対応：入力＝シーン（誕生日）・予算の下限と上限・タグ（4.2 検索画面）／候補取得＝誕生日シーン×予算の範囲×タグで商品DBから取得（6.2）／順位付け＝選んだタグとの類似度の高い順（6.2）／結果＝一致したタグ名つきの一覧（6.3）

| Phase1 で検証すること（要求定義書 6章との対応） | モックで確かめるのは、タグが正しく付くかと、検索結果が妥当か（6.4のテスト）<br>①人が見て合うと思う商品に、そのタグが付いているか<br>②タグを選んだとき、合う商品が上位に来るか<br>③タグごとに上位5%から10件（計50件）を選び、4人で説明文を読んでタグの付き方が合っているかを確かめる（「自信を持って選べるか」の確認の代わり。200件の正解データとの比較は、4人でタグ付けの感覚が違い正解を1つに決められないため、2026-11-21にやめた）<br>購入率・単価などの効果は、発表のあと本番に入れてから測る（要求定義書6章） |
| Phase2 以降 | ・Phase2：商品の詳細ページ、新商品への自動付与、誕生日以外のシーンに合わせたタグの組み合わせ、本番での効果測定（購入率・単価、BR-04・05）<br>・Phase3：家族への誕生日、送別（合意の支援）などへ広げる |

### 5.5 タグの付け方（手順）

タグは「準備（B）→ 機械でタグを付ける（②・③）→ 人が確かめる（④）」の順で付ける（指摘No23）。機械の計算は事前に1回だけ行って結果をDBに保存し、画面を開くたびに計算することはしない。

11/14の案にあったA（正解データ用の200件の取り分け）・C（言い回しの一覧）・①（言い回しでの分類）は、2026-11-21の打ち合わせで行わないことにした。記号（B・②〜④）は、ほかの章やコードが記号で参照しているため、11/14の案のまま残す。

- 準備
  - B. 決まり文句を取り除く
    - 手法：のし・ラッピング・配送のほか、年代・シーンの決まり文句と、申し込み方法・有効期限などの手続きの文を説明文から消す
    - 理由：全商品に共通する文が残ると、どの商品も同じように当たってしまうため
- 機械でタグを付ける（事前に1回だけ計算し、DBに保存）
  - ② e5で意味の近さを判定し、タグごとに上位5%を選ぶ
    - 手法：説明文を文ごとに分けてe5でベクトル（意味を表す数値の並び）にし、タグの計算用の説明文（match_text）との類似度（0〜1）を出す。一番高い文の類似度をその商品の類似度にし、その文を「根拠の一文（reason）」として残す。タグごとに類似度の上位5%を選ぶ（2026-11-21の打ち合わせで決定。④の評価で見直す）。境目と同じ類似度の商品は全部選ぶ
    - 理由：言い方が違っても意味が近い商品を拾える。類似度は全商品で0.80〜0.90に集まり、0.7程度以上では全商品に5つ全部のタグが付くため、決まった数字ではなく割合で選ぶ
    - 選んだあとに、次の2つを当てはめる
      - カタログギフトは②で選ぶ対象から外し、「定番で安心なものがいい」だけを付ける
      - 「ちょっと変わったものが好き」と「定番で安心なものがいい」が両方付いたら、ならした類似度（タグごとの平均からどれだけ高いか）の高い方を残す。外したものは一覧に出して人がときどき確かめる
  - ③ タグを付けてDBに保存する
    - 手法：②で選ばれた商品のタグを、類似度・根拠の一文と一緒にproduct_favoriteに保存する。人が入れた行と、人が確認した行は消さない。選ぶかどうかの境目の商品は一覧に出し、④で人が見る
- 人が確かめる
  - ④ チームで評価する
    - 手法：タグごとに上位5%から10件（計50件）を選び、4人で説明文を全部読んで、タグの説明と合っているかを確かめる
    - 理由：200件の正解データとの比較は、4人でタグ付けの感覚が違い、正解を1つに決められないためやめた
    - 結果（2026-11-21）：根拠の一文だけでは疑問が残るものもあったが、説明文全部を読むとタグの説明と合っていることを全員で確認し、タグ付けの結果は問題ないと結論づけた
    - 合わないときは、計算用の説明文や選ぶ割合（上位◯%）を直し、Bからやり直す
- 言い回しでの分類（C・①）を行わない理由：④の評価で、e5の結果がタグの説明と合っていることを確認し、6.4の検索の確認でも期待どおりの結果になったため（2026-11-21決定）。合いそうな商品にタグが付かないことがある課題は、付録Aに書いた
- そのあと
  - 新しい商品：登録時にB〜③を自動で流し、商品部が確認する（5.4）
  - それでも精度が足りないとき［未解決］：口コミ（reviews）もあわせてベクトルにする。Phase2で、言い回しの併用や選ぶ割合の見直しを検討する（付録A）

## 6. 候補の取り方と並び順（検索・絞り込み・ランキング）（with）

### 6.1 方式と選んだ理由

| 項目 | 内容 |
| --- | --- |
| 方式 | 絞り込み＋類似度による並べ替え。タグは意味検索（ベクトル）で事前に付けておき、画面を表示するたびにAIを呼ぶことはしない。LLM（文章を作るAI）は使わない |
| 選んだ理由 | ・同じ入力なら同じ順位になり、類似度という数字で「なぜこの順位か」を説明できる<br>・テストケースで良し悪しを確かめやすい<br>・画面を表示するたびにAIを呼ばないので、速度と費用が安定する<br>・要求定義書5章の案B（タグ）とそのまま対応する。予算の下限・上限は、既存の検索の条件（price_min・price_max）をそのまま使う |
| 選ばなかった方式と理由 | ・LLMでタグを付ける：LLMの「自信の度合い」は根拠を説明しにくく、同じ商品でも結果が変わることがある<br>・LLMで毎回提案を作る：出力が毎回変わり、順位の理由を説明・検証しにくい。費用と応答時間もかかる<br>・人気順（sales_count）で並べる：人気が自己強化され、Bさんにとっては「普通すぎる」になる（Exhibit 2）。既存のシーン別ランキングと変わらない（Exhibit 3）<br>・説明文のキーワード一致だけで絞る：説明文の書き方がばらばらで、表記ゆれに弱い（Exhibit 4） |

### 6.2 候補の取り方と順位の付け方

| 項目 | 内容 |
| --- | --- |
| 入力（ユーザーから受け取るもの） | ・予算の下限・上限（price_min、price_max。それぞれ500円単位で選ぶ）<br>・タグ（5種類から1〜2個。選ばなくてもよい）<br>・シーン（「誕生日」を選んだときだけタグ欄を出す） |
| 候補取得の条件 | ・product_scenes.scene_tag＝「誕生日」<br>・price_min ≦ price ≦ price_max<br>・stock＞0<br>・タグを選んだ場合：選んだタグのいずれかが product_favorite に付いている商品（タグは類似度がタグごとの上位◯%に入ったときだけ付けているので、検索時に類似度の条件は足さない） |
| 順位付けのロジック | 並び順＝選んだタグとの類似度の合計が高い順<br>・タグを2つ選んだ場合、両方が付いている商品は類似度を2つ足すので、自然に上に来る<br>・同点のとき、またはタグを選ばなかったときは、評価（rating）の高い順、さらにレビュー件数（review_count）の多い順<br>・sales_count（販売数）は使わない（人気が自己強化されるのを避けるため）<br>・既存の並び替え（おすすめ／人気／評価／価格／新着）との関係は、実装しながら検討。 |
| 使うデータ（テーブル.カラム） | products：product_id、product_name、price、stock、rating、review_count、description<br>product_scenes：scene_tag<br>product_favorite：tag_id、similarity<br>tag_id（タグの定義）：tag_name、definition |

### 6.3 推薦理由

| 項目 | 内容 |
| --- | --- |
| 理由の作り方 | ・理由の文章は作らない（AIでも定型文でも作らない）。タグを自分で選んで検索するので、商品カードに一致したタグ名を出せば、なぜこの商品が出たかは伝わると判断した。<br>・あわせて説明文（description）の冒頭2行を原文のまま表示する（行数は画面で調整）。<br>・類似度と根拠の一文（reason）は画面に出さず、DBに残して商品部の確認と後の分析に使う。DBにない特徴は書かない |
| 表示の例 | ［ちょっと変わったものが好き］［家でくつろぐ時間が好き］（選んだタグのうち、この商品に付いているもの）<br>¥4,800／★4.5（レビュー12件）<br>説明文の冒頭2行：「……」（原文のまま）　※文面は表示の例<br>レビューがない商品は、★の代わりに「レビューなし」と表示する（★0・「評価0」とは表示しない）。例：¥4,800／レビューなし |
